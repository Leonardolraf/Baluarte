## O que tem aqui
App real construído para a disciplina de Teste de Software do TCC (não mais stubs):

Testes em `backend/tests/` (`npm test`, 707 testes — 175 de unidade em `tests/unidade/` (sem banco), 10 de banco, 396 de integração, 126 de pentest em `tests/seguranca/` —; cobertura e relatório com `npm run test:relatorio` —, um banco `baluarte_test_<arquivo>` por arquivo, recriado pelas migrations; só roda contra Postgres local).

Porta `5173`. Suítes: Vitest + RTL + axe (`npm test`, 622 testes) e Playwright, a **suíte funcional oficial** do produto (B15): `npm run test:e2e` (46 testes em modo mock) e `npm run test:e2e:real` (21 testes contra a API real, pelo orquestrador `scripts/e2e-real.mjs`).
- `frontend/` — **frontend legado** (telas geradas do Figma). Porta `3000`. Mantido só como alvo das suítes Robot Framework da N2 AT1 (`e2e/*.robot`), que dependem das rotas `/cadastro-usuario`, `/cadastro-ativo`, `/campanha`, `/alterar-senha`, `/reset-senha` e dos ids dos formulários. Não evoluir; novas telas vão em `baluarte-frontend/`.
- `testes-api/` e `testes/api/` — collection Postman/Newman (N2 AT1): 35 requisições / 70 asserções sobre os 6 endpoints do contrato. Precisa de banco limpo (`db:reset` + `seed`, e reiniciar a API depois do reset).
- `testes/ui/` e `e2e/` — Robot Framework + Selenium (N2 AT1): 29 testes contra `frontend/` em `:3000`. Também precisam de banco limpo (o CT01 de ativo cadastra `10.0.0.5`).
- **Playwright × Robot:** o Playwright (`baluarte-frontend/e2e/`) é a suíte funcional oficial do produto e cobre as telas novas; o Robot fica só como a suíte da N2 AT1 contra o frontend legado e não ganha testes novos. Ver `README.md` deste repo para como rodar, credenciais de teste e como rodar cada suíte.

**Escopo honesto:** a plataforma (auth, RBAC, persistência, dashboard) é real. O scanner OWASP e o phishing são **simulados** — nenhum ataque real. A campanha envia um e-mail simulado por destinatário (`services/campanhaEmail.service.ts`: texto do template, rodapé identificando a simulação, links só para o frontend: `/t/<token>` treinamento e `/t/<token>/reportar`). Esse e-mail e os de conta (convite e redefinição de senha) saem via `config/email.ts`: API do **Brevo** quando `BREVO_API_KEY` existe (produção no Railway, que bloqueia SMTP), senão SMTP (Mailpit do Compose em `:8025`; Gmail na Vercel); nos testes, para a caixa em memória `caixaDeSaida`; em produção sem SMTP, nada sai nem é impresso.
- **Conta:** não existe senha provisória. `POST /users` cria a conta `Pendente` com hash de senha descartável e envia um convite (`services/linkConta.service.ts`, token tipo `CONVITE`, 72 h); conta `Pendente` não entra por login. Logout grava `sessaoEncerradaEm`; falhas de login ficam na tabela `LoginFailure`. Nos testes, `criarUsuario` aceita o convite com `SENHA_CONTA`; `criarUsuarioPendente` para antes.

## Regras do contrato
- As 6 rotas testadas pelo Postman (`POST /login`, `/scans`, `/assets`, `/users`, `/campaigns`, `GET /findings/classificacao`) e as mensagens/códigos de erro dessas rotas **não mudam** — só se estendem de forma compatível (ex.: `destinatarios[]` além de `destinatario` em `/campaigns`).
- **Estrutura (arquitetura em camadas, pedido do professor):** `backend/src/` tem uma pasta por camada e, dentro dela, um arquivo por funcionalidade (nomes em português, no singular: `auth`, `usuario`, `departamento`, `ativo`, `varredura`, `vulnerabilidade`, `campanha`, `treinamento`, `dashboard`, `notificacao`, `auditoria`, `agente`, `estacao`, `avisoMonitoramento`). O fluxo é **rota → controller → service → repository**: `routes/<f>.routes.ts` só declara caminho + middlewares (`exigeToken`/`exigePerfil`, em `middlewares/auth.middleware.ts`) + `wrap(controller.funcao)`, sem lógica nem validação; `controllers/<f>.controller.ts` tem uma função por endpoint: lê a requisição, valida a entrada com as regras zod do model (`validar(corpo, REGRAS)`, de `utils/esquemas.ts`, aplicadas na ordem do contrato), chama o service e monta a resposta (`enviar`/`erro`); `services/<f>.service.ts` tem a regra de negócio, chama o repository direto e lança `falhar(status, mensagem, código)` (`ErroNegocio`), que o `wrap` (`utils/resposta.ts`) converte no envelope de erro do contrato; `repositories/<f>.repository.ts` é o único lugar que fala com o Prisma (`config/db.ts`). `models/<f>.model.ts` não é ORM (o banco é do Prisma): são os tipos do domínio (derivados do `@prisma/client`), os DTOs e as listas de regras zod de entrada; também ficam ali os dados estáticos do domínio (`dominio.model.ts`, `catalogoAchado.model.ts`, `treinamento.model.ts`). Auxiliares de regra são services com nome próprio (`token.service.ts`, `linkConta.service.ts`, `cvss.service.ts`, `cicloVarredura.service.ts`, `campanhaEmail.service.ts`, `campanhaMetricas.service.ts`, `auditoria.service.ts`, `relatorioVulnerabilidade.service.ts`, `relatorioPdf.service.ts`, `riscoAtivo.service.ts`, `indiceRisco.service.ts`, `evolucaoRisco.service.ts`). `config/` tem o Prisma, o e-mail e os clientes externos (ClamAV, VirusTotal, OSV, NVD; URL base sobrescrevível por variável de ambiente para os testes usarem um servidor falso local); `utils/` o envelope de resposta, os schemas zod, os predicados de validação e os tokens de link. `src/app.ts` (o app Express) fica na raiz de `src` porque o preset Express da Vercel o procura ali e exige o import do express nesse arquivo; `src/server.ts` sobe o servidor. Endpoint novo: regra no model, função no controller, regra de negócio no service, consulta no repository e a linha na rota. A ordem de registro está em `src/routes/index.ts` (em `treinamento.routes.ts`, `/treinamentos/consolidado` vem antes de `/treinamentos/:token`). Toda rota de escrita registra em `AuditLog` (`services/auditoria.service.ts`), inclusive `POST /assets` (`CRIAR_ATIVO`) e `POST /scans` (`INICIAR_VARREDURA`) do contrato; só grava depois que a ação deu certo.
- O frontend fala com o backend só por `baluarte-frontend/src/services/api.ts` + `adapters.ts` (envelope `{ status, dados, resumo }`, campos em português → modelos de domínio em inglês).
- **RBAC é do servidor:** `exigeToken` carrega o usuário do banco a cada requisição (perfil atual, conta removida/inativa, senha redefinida) e `exigePerfil` decide pelo perfil do banco, não pelo que está no JWT. Administrador gerencia usuários; Analista opera a plataforma e lê as listas técnicas; Colaborador só vê o índice de resiliência a phishing no dashboard (KPIs técnicos, inclusive `arquivosMaliciosos`, e `distribuicaoSeveridade` vêm `null`, RN-006), a política e o próprio treinamento. A regra do último administrador conta só admin com status `Ativo` (Pendente não entra, logo não garante acesso). Ver a tabela no `README.md`.
- **Campanha ↔ usuário:** destinatário só do domínio interno (`DOMINIO_INTERNO` do ambiente, padrão `@empresa.com`, lido por `dominioInterno()` em `models/dominio.model.ts`) e cadastrado. `CampaignEvent.userId` é obrigatório (só destinatário cadastrado e não inativo), com unicidade (`campaignId`, `userId`); usuário com histórico de campanha não é excluído (`USUARIO_COM_HISTORICO`); nem quem tem ciência do aviso de monitoramento (`USUARIO_COM_CIENCIA`, B18). O dono do treinamento é decidido pelo `userId`, nunca pelo e-mail.
- **Dois acessos ao treinamento:** dentro do sistema, `/treinamentos/:token` usa o id do evento e exige login; o link do e-mail usa `/treinamentos/link/:token` (e `/reportar`, POST público e idempotente), com token aleatório guardado só como hash (`utils/tokens.ts`, o mesmo do reset de senha). No frontend, as rotas públicas `/t/:token` e `/t/:token/reportar` consomem esses endpoints.
- **Ativos (B10):** `POST /assets` normaliza o host colado com `http(s)://` (`normalizarHost` em `utils/validacao.ts`: tira esquema, caminho, query, porta e barra final) antes das regras do contrato; sem esquema, nada muda. `ip` (IPv4) e `descricao` (até 500) são opcionais, validados depois das regras do contrato (`IP_INVALIDO`, `DESCRICAO_INVALIDA`), com CHECK no banco, e voltam no POST e no `GET /assets`.
- **Achados:** a nota CVSS sai do vetor (`services/cvss.service.ts`), nunca é digitada; tipos de falha, CWE, CVE e remediação ficam no catálogo `models/catalogoAchado.model.ts` e são copiados para o `Finding` no momento do achado. `remediacao` é `Json` (JSONB).
- **Varredura simulada (B21):** status por tempo decorrido, avaliado e gravado na leitura (`services/cicloVarredura.service.ts`: `EM_FILA` 5 s → `EM_ANDAMENTO` até 20 s → `CONCLUIDA`), sem timer em segundo plano (a API também roda serverless). **É uma máquina de estados avaliada na leitura, não um worker:** quem avança é `avancarVarreduras`, chamado por `GET /scans`, `GET /scans/:id`, `/dashboard` (qualquer perfil, via `vulnerabilidade.service.panoramaAbertos`), `/assets`, `/vulnerabilidades` e `POST /scans`; para o usuário o efeito é de segundo plano. Worker de verdade só no modo real (W01/W09). Os achados nascem só na conclusão. `POST /scans` continua respondendo `EM_FILA` (sem campos novos; o Newman confere) e recusa nova varredura no mesmo ativo enquanto a anterior não conclui (`409 VARREDURA_EM_ANDAMENTO`, RN-003).
- **Progresso da varredura (B26):** `progressoDaVarredura` (mesmo arquivo) deriva `progresso` (0 fila / 1–99 andamento / 100 concluída), `etapa` (`ETAPA_FILA`, `ETAPAS_ANDAMENTO` distribuídas por igual no andamento, `ETAPA_CONCLUIDA`) e `estimativaConclusao` de `criadoEm`, das constantes e do status **gravado** (concluída é sempre 100, andamento nunca passa de 99), sem gravar nada; o service usa o mesmo `agora` para avançar e calcular. Sai em `GET /scans` e `GET /scans/:id` (`CONSULTA` em `models/varredura.model.ts`, id `idRecurso` de `utils/esquemas.ts`; `400 VARREDURA_ID_INVALIDO`, `404 VARREDURA_NAO_ENCONTRADA`). No frontend, `ScanReport.progress/stage/estimatedCompletionAt`, `api.getScan` e a tela `/scans` consultam só as varreduras em curso; o mock espelha a lógica em `src/mocks/scanProgress.ts` (a `scan-005` do seed é uma varredura longa, com progresso fixo e sem estimativa).
- **Dashboard agregado no banco (B30, RNF-004):** `GET /dashboard` nunca carrega a lista inteira de achados. `panoramaAbertos` (`repositories/vulnerabilidade.repository.ts`) devolve a contagem por severidade dos achados em aberto, quantos têm nota ≥ 9,0 e só os 5 mais recentes (ordem `criadoEm` desc, `id` desc); os alertas são os 3 primeiros desses. A evolução de 30 dias (B25b) também tem custo controlado: `abertosPorDia` lê o histórico como trechos (ver o item do B25b) e `evolucaoRisco.service.ts` reaproveita um `Intl.DateTimeFormat` por fuso (criar um por chamada custava ~5 ms de CPU por leitura, na thread da API). `tests/dashboard.test.ts` confere os dois contra a regra calculada sobre todos os achados. Com 1.200 achados e 200 conexões, o p90 do dashboard era 8,75 s sem o B30 e ficou em ~1,35 s (`testes/carga/RELATORIO.md`). **Nova leitura no dashboard = rodar `npm run carga` de novo.**
- **Idioma do banco:** os campos são em português, exceto o modelo `Department` (`name`, `createdAt`) e `User.departmentId`, por decisão do projeto. A API continua em português (`departamento`).
- **Auditoria (B12, RN-008):** a ação é texto livre (código em maiúsculas, ex.: `ANALISAR_ARQUIVO`), sem CHECK nem lista fixa: a consulta `GET /auditoria` (só Administrador) devolve em `resumo.acoes` as ações distintas e a tela `/audit` do frontend usa essa lista e `lib/audit.ts` (rótulo conhecido ou derivado do código), então ação nova não exige mudança na consulta nem na tela. O `AuditLog` não tem FK para `User` de propósito (o registro sobrevive à exclusão); o autor é buscado pelos ids e sai `null` quando não existe. Filtros, paginação (`tamanho` ≤ 100) e período vão para o servidor; a query é validada por `CONSULTA` em `models/auditoria.model.ts` (objeto/array como `?acao[$ne]=x` dá 400, nunca 500).
- **AuditLog é só inserção pela aplicação, com cadeia de hash (B29, RNF-002):** a aplicação nunca faz `update`/`delete`/`deleteMany` no `AuditLog`, nem em teste (teste que precisa de trilha limpa usa o próprio banco; o de adulteração mexe direto no banco, dentro da transação). `sequencia`, `hashAnterior` e `hash` são do trigger `BEFORE INSERT` (`auditoria_encadear`, sob `pg_advisory_xact_lock`), nunca da aplicação; a fórmula fica só na função SQL `auditoria_calcular_hash`, que `GET /auditoria/integridade` também usa (serialização no README). A ordem da cadeia é a `sequencia`, não o `timestamp`; o default dela é `0` e quem tira o `nextval` é só o trigger, dentro do lock (default `nextval` gastaria dois números por INSERT; a sequence `AuditLog_sequencia_seq` fica sem dono para o Prisma não pedir `DROP SEQUENCE`). Retenção de 12 meses (`RETENCAO_MESES`) só por `auditoria_aplicar_retencao()` (`POST /auditoria/retencao` ou `npm run auditoria:retencao`), que apaga o prefixo antigo da cadeia; o primeiro registro restante é a âncora. **Redação:** a trilha tem "cadeia de hash com verificação de integridade (detecta adulteração)"; não é "imutável": o banco ainda aceita UPDATE/DELETE de quem tem a connection string. A trava no banco (migration `20261008176000_auditoria_imutavel`, porta de mão única) fica na branch `feat/b29-trava` e **só entra depois da apresentação** (decisão do Leo, 10/10/2026); até lá vale a redação acima. `logImutavel` da política e `travaNoBanco` consultam os triggers e saem `false` sem ela.
- **Relatório de vulnerabilidades em PDF (B24, US-011):** `GET /vulnerabilidades/relatorio.pdf` (Administrador/Analista; registrada antes de `/vulnerabilidades/:id`). Os filtros são os da lista, validados por `FILTROS_RELATORIO` (`models/vulnerabilidade.model.ts`; inválido → 400 `SEVERIDADE_INVALIDA`/`STATUS_INVALIDO`/`BUSCA_INVALIDA`) e aplicados no banco pelo mesmo `where` da lista (`repositories/vulnerabilidade.repository.ts#filtro`), mas **sem paginar** (`listarFiltrados`): o PDF leva todos os achados do filtro. Montar os dados (`relatorioVulnerabilidade.service.ts`, puro e testável) é separado de desenhar (`relatorioPdf.service.ts`, `pdfkit` 0.17.2 fixo, em memória, fontes padrão em WinAnsi: texto fora dela passa por `paraWinAnsi`). Datas no fuso `America/Sao_Paulo`. Grava `EXPORTAR_RELATORIO_VULNERABILIDADES` depois que o PDF ficou pronto. O arquivo sai por `enviarArquivo` (`utils/resposta.ts`, `no-store`). Nos testes, `tests/pdf.ts` extrai o texto do PDF sem biblioteca. No frontend o download é Blob pelo `httpClient` (o interceptor lê o envelope de erro de dentro do Blob); no modo mock, `src/mocks/pdf.ts` monta um PDF simples só de texto.
- **Lista de vulnerabilidades (B25):** `GET /vulnerabilidades` filtra, ordena e pagina **no banco** (`listarPagina`: `where` + `orderBy` + `skip`/`take` + `count`/`groupBy`), nunca em memória. Query validada por `CONSULTA_LISTA` (filtros do B24 + `regrasDePaginacao(TAMANHO_MAXIMO)` de `utils/esquemas.ts`, a mesma da auditoria e do B17, + `ordenar` `detectadoEm|cvss|descricao` e `direcao`; inválido → 400 com código próprio). Página padrão 20, máximo 100; sem `ordenar`, a mais recente primeiro. Ordem sempre estável: campo pedido, `criadoEm` desc, `id`. O `resumo` (`total`, `ativos`, `pagina`, `tamanho`, `porSeveridade`, `porStatus`) é do filtro inteiro, não da página. A busca `q` escapa `\`, `%` e `_` antes do `contains` (o Prisma não escapa). No frontend, `api.listVulnerabilities(filtros, { page, pageSize, sort })` e `VulnTable` com `server`.
- **Pesos de severidade únicos (B25b):** `PESO_SEVERIDADE` em `models/dominio.model.ts` é o **único** lugar que define a escala de risco (escala 10/7/4/1, piso da faixa CVSS 3.1, **aprovada pelo Leo em 10/10/2026, cartão DT07**). Nota por ativo, índice global e evolução usam `services/indiceRisco.service.ts` (`pontosDeRisco`, `indiceRiscoTecnico`); não repetir números de peso em outro arquivo do backend nem criar fórmula no frontend (o mock espelha a constante em `RISK_WEIGHT`, como servidor simulado). Trocar a escala = mudar só a constante e o teste de unidade que a fixa.
- **Nota de risco por ativo (B25):** `services/riscoAtivo.service.ts`, calculada a **cada leitura** e nunca gravada (por isso acompanha toda mudança sem gatilho): `pontos` = soma de `PESO_SEVERIDADE` × abertos de cada severidade, só dos achados abertos (fora "Resolvida" e "Risco aceito", a mesma regra dos KPIs) e `nota = min(100, pontos)`. Arquivo malicioso (B17) não entra: não é achado de ativo. As contagens vêm de uma consulta agrupada (`contarAbertosPorAtivo`, `$queryRaw` com `Prisma.join`). Sai em `GET /assets` (`notaRisco`, `abertosPorSeveridade`, `achadosAbertos`, ao lado de `ip`/`descricao`) e em `GET /dashboard` como `ativosMaiorRisco` (5, ordem: nota, pontos sem teto, críticos→baixos, nome, id). Para o Colaborador, `ativosMaiorRisco: []`, como as outras listas técnicas (os KPIs técnicos dele vêm `null`, B10).
- **Índice global e evolução do risco (B25b):** `kpis.indiceRiscoTecnico = min(100, round(pontos / (max(1, ativos) × 20) × 100))` é calculado no backend sobre a `distribuicaoSeveridade` (que já tem os arquivos maliciosos no Crítico); o frontend só exibe (`adapters.ts#toDashboard` lê o número, sem fórmula). `evolucaoRisco` (`services/evolucaoRisco.service.ts`) reconstrói os últimos 30 dias **na leitura, sem cron nem foto**: dia no fuso `America/Sao_Paulo`, terminando 1 ms antes da meia-noite local seguinte (hoje termina agora); um achado conta no dia se foi criado até ele e o último evento de `FindingStatusChange` até ali o deixa aberto; **no ponto de hoje vale `Finding.status`**, então o último ponto é sempre igual aos KPIs. **Contagens:** `critico/alto/medio/baixo` só de achados (`vulnerabilidade.repository.ts#abertosPorDia`, uma consulta: o histórico vira trechos de status com `LEAD`, cada trecho aberto vira uma faixa de dias por `width_bucket` sobre os fins dos dias, e um vetor de diferenças acumulado dá a contagem de cada dia; B30), `arquivosMaliciosos` = a regra do B17 com a janela de 30 dias terminando no dia, `ativos` = ativos criados até o dia (todos, como o KPI), `indice` = a fórmula do KPI com os arquivos somados ao Crítico. Custo proporcional ao número de eventos do histórico, não a 30 × achados (B30: com 1.200 achados, de ~125 ms para ~10 ms; `tests/dashboard.test.ts` confere contra a regra "último evento até o fim do dia", com empate no mesmo instante e achado sem evento). Colaborador: `indiceRiscoTecnico` e `evolucaoRisco` vêm `null`.
- **Histórico de status do achado (B25b):** tabela `FindingStatusChange` (`findingId` FK cascade, `de` nulo na criação, `para`, `usuarioId` sem FK como no `AuditLog`, `registradaEm`, `id` sequencial), CHECK de status (a lista de `STATUS_FINDING`; `de <> para`; criação só para `Aberta`) e RLS. **Toda escrita de status grava o evento na mesma instrução SQL** (`vulnerabilidade.repository.ts#alterarStatus`, CTE com `FOR UPDATE` na linha do achado; o instante do evento é `clock_timestamp()` em UTC, lido já com a linha travada, nunca o default `now()` da coluna, que é o início da instrução e deixava a cadeia fora de ordem sob concorrência) e **todo caminho que cria `Finding` grava o evento de criação** na transação dos achados (`registrarCriacaoDosAchados`: `varredura.repository.ts#concluirComAchados` e `estacao.repository.ts#registrarAchados`); caminho novo que cria achado ou muda status precisa fazer o mesmo, senão o histórico e a evolução ficam errados. A migration `20261008180000_historico_status_achado` preencheu o passado (criação de todo achado + mudanças lidas do texto de `ALTERAR_STATUS_VULNERABILIDADE`); a aba de histórico (`vulnerabilidade.service.ts#historico`) lê só a tabela, então o texto da auditoria pode mudar. `completo` = as mudanças saem de "Aberta" e chegam no status atual; senão o frontend avisa.
- **Banco:** mudança de schema só por migration (`npm run db:migrate:dev -- --name <nome>`), nunca `db push`. Valores fixos (perfil, status, tipo, severidade, template) são texto com restrição **CHECK** escrita à mão na migration (o Prisma não modela CHECK; `migrate diff` confirma que ele não tenta removê-las) — mudar uma lista de `src/models/dominio.model.ts` exige migration nova. E-mail e nome de departamento são `citext`. Caractere NUL é barrado na borda (`src/app.ts`), porque o Postgres o recusa; só nas rotas do agente ele é removido dos valores em vez de recusado (B08).
- **Docker:** `docker compose up --build -d` sobe Postgres, API `:8080`, frontend do produto `:8081` (Nginx) e legado `:3000`. ## Segurança
Nunca deixar segredo hardcoded (chave/token/senha) no código — usar `.env` (fora do git; ver `.env.example` em `backend/`, `frontend/` e `baluarte-frontend/`). Senhas só com bcrypt; tokens de redefinição só como hash SHA-256 no banco. Para serviços externos de análise (VirusTotal), só sai o hash do arquivo, nunca o conteúdo.
**Certificados e chaves TLS ficam fora do git:** `certs/` está no `.gitignore` (só `certs/servidor/.gitkeep` é versionado), assim como `*.key` e `*.pem` em qualquer pasta. A chave da CA (`certs/ca.key`) nunca é commitada, copiada para contêiner ou distribuída; o que se entrega a navegador e agente é só `certs/ca.crt`.
